# LINE AI 智慧客服(跨行業)— 設計文件

日期:2026-09-21
狀態:設計完成,待實作
用途:求職專題 / 面試現場 demo

一句話:**企業把自己的資料放進一個資料夾,不改任何一行程式碼,就得到一個掛在 LINE 官方帳號上的 AI 客服。**

---

## 一、目標與範圍

### 做(本 spec 涵蓋:子系統 1 + 2)

1. **LINE ↔ Dify bridge** —— 跑在 Cloudflare Worker 上的接線層。收 LINE webhook、驗簽章、呼叫 Dify、把答案送回 LINE。
2. **資料驅動的客服 app** —— 行業無關的 YAML 資料層 + build 管線,產出可匯入 Dify 的 DSL。換行業只換一個資料夾。
3. **三個示範行業**:餐飲、電商、診所。

**本階段的里程碑**:拿手機傳訊息給 LINE 官方帳號,一個不綁行業的客服會用餵進去的資料回答,而且換一個 `--industry` 參數重 build 就變成另一個行業。

### 不做(各自另開 spec)

| 子系統 | 為什麼延後 |
|---|---|
| Qdrant + Contextual Retrieval 外部知識庫 | 要公開 HTTPS 託管,是獨立問題。第一版先用 Dify 內建知識庫,之後換掉不會白做 —— Dify 的外部知識庫是可抽換的介面 |
| 結構化資料 + Text2SQL | 要先知道客服真正會被問什麼查詢,才知道 schema 該長怎樣 |
| 對話紀錄 + 分析報表 | 要先有真的對話才有東西可分析 |

### 明確不做(YAGNI)

- 多租戶:一家企業一份部署,不做租戶隔離、後台、計費、登入
- 圖片 / 貼圖 / 語音訊息:第一版只處理文字
- 群組對話:只處理 1 對 1
- 真人接手介面:`escalation` 只負責「判斷該轉」並告知客人,不做客服後台

### 聲明

這是**面試用的專題**,不是營運系統。取捨因此是:

- **成本不重要、防濫用不重要** —— 但 **demo 不能開天窗**。網路或 Dify 出狀況時,它必須講一句得體的話,不能已讀不回。
- **要有故事可講** —— 架構的每個決策都要能用一句話解釋「不這樣做會怎樣」。這份文件本身就是面試素材。

## 二、決策紀錄

| # | 決策 | 理由 / 不這樣做會怎樣 |
|---|---|---|
| 1 | Webhook 收到就回 200,實際工作丟 `ctx.waitUntil()` 背景執行 | LINE 沒收到 2xx 會重送。同步等 Dify(3–15 秒)必定超時,客人會收到兩次一樣的答案 |
| 2 | 回覆以 `replyToken` 為主,超時改用 push | reply token **只有一分鐘、只能用一次**,官方還明講「不要依賴這個時限來實作」。但 push 會吃掉官方帳號的推播額度,reply 不會 —— 所以不能乾脆全用 push |
| 3 | 用 `webhookEventId` 去重,KV 存 10 分鐘 | LINE 重送時會重複回答,而且會發生在面試演到一半的時候。`deliveryContext.isRedelivery` 只是提示,真正的去重要靠 event id |
| 4 | 簽章用 **raw bytes** 計算 | `await request.text()` 取原始字串算 HMAC。parse 再 stringify 會改變位元組,簽章永遠對不上。自己造假資料測會過、LINE 真的傳過來會壞 |
| 5 | Dify 用 `blocking` 而非 `streaming` | LINE 不能逐字顯示,串流碎片最後還是要拼成一則訊息,徒增複雜度 |
| 6 | 第一版只產「單節點版」DSL | 沿用 `bistro_concierge/src/build_dsl.py` 的既有原則:一次把多條支線全推上線,出問題時分不清是哪一段壞的 |
| 7 | 獨立 repo,不併入 `bistro_concierge` | 那個專案的故事是「餐飲深度」,這個是「跨行業通用」。混在一起兩邊都講不清楚 |
| 8 | 所有密鑰讀進來一律 `.trim()` | 實戰教訓:secret 貼上時黏到尾端換行,HTTP header 含換行會被整個丟掉,上游回的錯誤訊息完全指不到真正原因 |

## 三、整體架構

```
                    ┌──────────────── 企業帶入的資料 ────────────────┐
                    │  industries/<行業>/  ← 五份 YAML,唯一真相來源  │
                    └────────────────────┬───────────────────────────┘
                                         │  python build.py --industry <行業>
                                         ▼
                              dist/<行業>_客服.yml
                                         │  手動匯入
                                         ▼
  LINE 官方帳號 ◄──── Cloudflare Worker ────► Dify Cloud
       ▲    │              (bridge)              (客服 app)
       │    │                  │
       │    └── webhook ───────┘
       └────── reply / push ───┘
```

兩個子系統的邊界很乾淨:**bridge 完全不知道客服在講什麼行業**,它只負責搬運訊息與維持對話狀態;**資料層完全不知道前台是 LINE**,它只負責產生一個 Dify app。任一邊都可以單獨替換 —— 之後要加 Web 聊天視窗,只是多一個 bridge。

## 四、子系統一:LINE ↔ Dify bridge

### 4.1 執行環境

Cloudflare Worker。選它的理由不是它最好,是**這是唯一一條已經驗證過、會動的路**(既有的 `restaurant-voice-ivr` Worker 已成功部署,wrangler 也設定完成)。面試專題不該在託管方式上冒險。

### 4.2 端點

| 路徑 | 方法 | 用途 |
|---|---|---|
| `/line/webhook` | POST | LINE 事件入口。唯一對外的端點 |
| `/health` | GET | 回 `ok` + 版本。用來確認部署成功,不洩漏任何設定 |

### 4.3 資料流

```
LINE ──POST /line/webhook──> Worker
   │
   │ 1. 讀 raw body(字串,不 parse)
   │ 2. 驗 X-Line-Signature = base64(HMAC-SHA256(CHANNEL_SECRET, raw body))
   │       不符 → 401,結束
   │ 3. parse JSON。events 為空陣列 → 200 結束
   │       (Console 按「Verify」時就是送空 events + 全 0 的 replyToken)
   │ 4. 逐一檢查 webhookEventId 是否在 KV → 看過就跳過
   │ 5. ★ 立刻回 200
   │
   └─ ctx.waitUntil() ─┐
                       │ 6. 只處理 type=message 且 message.type=text 的事件
                       │ 7. KV 取 conv:{userId} → conversation_id(可能沒有)
                       │ 8. POST Dify /v1/chat-messages(blocking)
                       │ 9. 回存 conv:{userId} = 回傳的 conversation_id
                       │10. 標記 seen:{webhookEventId}
                       └11. reply(替代:push)──> LINE ──> 客人
```

### 4.4 狀態(Workers KV,只有兩種鍵)

| 鍵 | 值 | TTL | 沒有它會怎樣 |
|---|---|---|---|
| `conv:{lineUserId}` | Dify `conversation_id` | 30 天 | **客服會失憶**。客人說「那我要退貨」,它會反問「請問您是哪位」 |
| `seen:{webhookEventId}` | `1` | 10 分鐘 | LINE 重送時重複回答 |

### 4.5 密鑰(`wrangler secret put`,四個)

| 名稱 | 說明 |
|---|---|
| `LINE_CHANNEL_SECRET` | 驗簽章用 |
| `LINE_CHANNEL_ACCESS_TOKEN` | 呼叫 reply / push 用 |
| `DIFY_API_KEY` | Dify app 的 API key(`app-` 開頭) |
| `DIFY_BASE_URL` | 預設 `https://api.dify.ai/v1`,自架時改這裡 |

讀取時一律 `.trim()`(決策 8)。

### 4.6 上游 API 契約

**Dify**

```
POST {DIFY_BASE_URL}/chat-messages
Authorization: Bearer {DIFY_API_KEY}
{ "inputs": {}, "query": "<客人的話>", "response_mode": "blocking",
  "conversation_id": "<可為空字串>", "user": "<LINE userId>" }
→ { "answer": "...", "conversation_id": "...", "message_id": "..." }
```

`user` 直接用 LINE 的 userId —— Dify 後台就能按使用者看對話,不用另外對照表。

**LINE**

```
POST https://api.line.me/v2/bot/message/reply
{ "replyToken": "...", "messages": [{ "type": "text", "text": "..." }] }

POST https://api.line.me/v2/bot/message/push
{ "to": "<userId>", "messages": [{ "type": "text", "text": "..." }] }
```

兩者都帶 `Authorization: Bearer {LINE_CHANNEL_ACCESS_TOKEN}`。

## 五、四個必須擋掉的坑

### 1. 簽章用序列化過的 body 計算

最常見、也最難查。必須用收到的原始位元組。自己寫測試造資料時兩邊都用同一個序列化器,所以一定會過;LINE 真的傳過來(欄位順序、空白、Unicode 跳脫都可能不同)就會全錯。**測試必須包含一組「已知 body 字串 + 已知 secret + 已知簽章」的固定樣本。**

呼應既有教訓:語音 demo 的所有測試都用 stub 跑,真的 SpeechRecognition 一次都沒驗過,結果桌機全過、實機全壞。

### 2. 答案超過 LINE 的訊息長度上限

Dify 講起話來可能很長,LINE 單則文字訊息有長度上限(5000 字元)。超過會整則失敗 —— **客人什麼都收不到**,而且錯誤只出現在 Worker log 裡。**處理方式是截斷,不是分則**:分則會讓客人收到一串沒頭沒尾的訊息,而客服答案本來就不該那麼長 —— 會超過上限本身就是資料寫壞了,應該在 validate 階段就發現。

### 3. reply token 過期後沒有退路

一分鐘是官方說的、而且說了不要依賴。Dify 偶爾會慢。沒有 push 退路的話,慢的那一次就是徹底沉默。

### 4. `waitUntil` 的執行時間上限

背景工作不是無限期的。等待 `fetch` 屬於 I/O 而非 CPU 時間,正常情況沒問題,但要在實作時實測一次 Dify 回應 20 秒以上的情境,確認 Worker 沒有被提前砍掉。**這一項列為實作時必須驗證的假設,不是已知事實。**

## 六、子系統二:資料層與 build 管線

### 6.1 目錄結構

```
universal-ai-helpdesk/
├── industries/
│   ├── restaurant/     ← 餐飲
│   │   ├── company.yaml
│   │   ├── faq.yaml
│   │   ├── policies.yaml
│   │   ├── escalation.yaml
│   │   └── glossary.yaml
│   ├── ecommerce/      ← 電商(同樣五份)
│   └── clinic/         ← 診所(同樣五份)
├── prompts/
│   └── system.j2       ← 唯一的樣板,行業無關
├── src/
│   ├── build_prompt.py
│   ├── build_dsl.py
│   ├── validate.py
│   └── common.py
├── dist/               ← 產出,可匯入 Dify
├── worker/             ← 子系統一
└── build.py            ← python build.py --industry clinic
```

`industries/` 底下每個資料夾的結構完全相同。**新增一個行業 = 複製一個資料夾、改裡面的 YAML、重跑 build。這就是「帶入資料就能使用」的具體意思。**

### 6.2 五份 YAML

| 檔案 | 內容 | 必填欄位 |
|---|---|---|
| `company.yaml` | 公司名、業別、營業時間、聯絡方式、語氣風格、**禁語清單** | `name` `industry` `hours` `contact` `tone` `forbidden_phrases` |
| `faq.yaml` | 常見問答。量最大的一份 | 每筆 `q` `a`,`a` 不可為空 |
| `policies.yaml` | 退換貨、保固、預約、付款、隱私 | 每條 `title` `content` |
| `escalation.yaml` | 分級與轉真人規則 | 每條 `level`(L1/L2/L3)`trigger` `action` `script` |
| `glossary.yaml` | 行業術語表,避免模型講錯專有名詞 | 每筆 `term` `meaning` |

`escalation.yaml` 是這裡最值錢的一份。客訴分級、什麼情況必須轉真人、什麼話絕對不能說 —— 這套規則跨行業通用,但**只有真的在第一線處理過客訴的人寫得出來**。這是整個專題裡別人抄不走的部分,結構沿用 `bistro_concierge/knowledge/complaints.yaml` 的 L1/L2/L3 階梯。

### 6.3 build 管線

```
industries/<行業>/*.yaml
    → build_prompt.py (Jinja2)  → prompts/build/<行業>_system.md
    → build_dsl.py              → dist/<行業>_客服.yml
    → validate.py               → BLOCK / ERROR 清單
一鍵:python build.py --industry <行業>
```

形狀沿用 `bistro_concierge`(已驗證可行),差別只在**行業從寫死變成參數**。validate 有 ERROR 時回傳非零離開碼,可掛 CI 或 git pre-commit。

### 6.4 validate 規則

兩個等級的意思不同,不要混用:

- **ERROR** = 資料壞了。**擋 build**,回傳非零離開碼。
- **BLOCK** = 資料沒壞,但**不該就這樣交給客戶上線**。不擋 build(你仍然可以 build 出來自己測),但會列在報告最上方,必須在導入會議上跟客戶確認過才算解除。

| # | 檢查 | 等級 |
|---|---|---|
| 1 | 五份 YAML 都存在且可 parse | ERROR |
| 2 | 必填欄位齊全(見 6.2) | ERROR |
| 3 | **FAQ 的答案本身不可命中自己的 `forbidden_phrases`** | ERROR |
| 4 | `escalation` 必須涵蓋四類高風險情境:法律、醫療/人身安全、金錢爭議、個資 | BLOCK |
| 5 | 殘留 placeholder(`請填入` / `TODO` / `XXX`) | BLOCK |
| 6 | `glossary` 的術語不可與禁語清單衝突 | ERROR |
| 7 | 營業時間格式可解析 | ERROR |

**BLOCK 不是 bug,是導入會議的議程。** 這是面試時最值得講的一句話:交付的不是機器人,是一份檢查清單 —— validate 跳出來的每一條,都是要跟客戶確認的問題。(概念沿用 `bistro_concierge/src/validate.py` 的 17 項 BLOCK。)

## 八、錯誤處理與降級

| 情況 | 行為 |
|---|---|
| 簽章不符 | 401,不處理,不回訊息 |
| `events` 為空(Console 的 Verify) | 200,結束 |
| 非文字訊息(圖片/貼圖/語音) | 回一句「我目前只看得懂文字訊息」 |
| 重複的 `webhookEventId` | 略過,不回訊息 |
| Dify 逾時 / 5xx / 回傳空答案 | 回 fallback:「我這邊剛剛連線有點問題,可以再問一次嗎?」 |
| 答案超過長度上限 | 截斷並附「(訊息過長已截斷)」 |
| reply 失敗(token 過期或已用) | 改用 push 送同一則 |
| push 也失敗 | 寫 log,放棄。不再重試 —— 重試只會讓客人收到延遲很久的孤立訊息 |

**原則:任何情況下客人都要收到一句話。沉默是唯一不被接受的失敗模式。** 這對面試 demo 尤其重要 —— 網路出狀況時它講了一句得體的話,比它答對十題更能說明設計者想過真實情境。

## 九、測試策略

**子系統一(Worker)** — `vitest` + `@cloudflare/vitest-pool-workers`,在真的 Worker runtime 裡跑。

| 測什麼 | 怎麼測 |
|---|---|
| 簽章驗證 | **固定樣本**:已知 body 字串 + 已知 secret + 已知簽章。這一條是防第五節第 1 坑的唯一手段 |
| 簽章不符 | 回 401 且完全不呼叫 Dify |
| 去重 | 同一個 `webhookEventId` 送兩次,Dify 只被呼叫一次 |
| 空 events | 回 200 且不呼叫 Dify |
| conversation 延續 | 第二次請求要帶上第一次回傳的 `conversation_id` |
| Dify 逾時 | 走 fallback 文案,而且**有送出訊息** |
| reply 失敗 | 自動改走 push |
| 長訊息 | 超過上限會截斷 |

只 mock `fetch`(對 Dify 與 LINE 的呼叫),其餘都跑真的。

**子系統二(build 管線)** — `pytest`。

| 測什麼 |
|---|
| 三個行業都能 build 成功、validate 零 ERROR |
| 故意抽掉必填欄位 → 出現對應的 ERROR |
| 故意讓 FAQ 答案命中禁語 → 第 3 條規則抓得到 |
| 故意拿掉 escalation 的醫療情境 → 第 4 條 BLOCK 抓得到 |
| 產出的 DSL 是合法 YAML,且節點 id、邊、變數參照三者一致 |

**端對端** — 手動,但必須做:LINE Console 按 Verify 通過 + 真的用手機傳三則訊息(一般問答、觸發 escalation 的問題、非文字訊息)。

> 這一項不可省略。既有教訓:所有語音測試都用 stub 跑,真實裝置一次都沒驗過,結果桌機全過、實機全壞。

## 十、驗收標準

1. `python build.py --industry restaurant|ecommerce|clinic` 三個都成功,validate 零 ERROR
2. 三份 DSL 都能匯入 Dify 而不報錯
3. LINE Console 的 Webhook「Verify」顯示成功
4. 手機傳訊息,收到符合該行業資料的回答。典型 10 秒內;超過 60 秒仍要收得到(走 push 那條路)
5. 連續兩則訊息,第二則看得出記得第一則的內容(對話延續)
6. 診所版問「我這個症狀是不是癌症」→ 觸發 escalation,拒答並提供轉真人指引
7. 故意把 `DIFY_API_KEY` 改壞 → 客人收到 fallback 文案,不是沉默
8. 全部自動測試通過
