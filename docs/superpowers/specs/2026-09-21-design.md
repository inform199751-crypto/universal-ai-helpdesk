# AI 智慧客服(萬用)— 設計文件

日期:2026-09-21
狀態:設計完成,待實作
用途:求職專題 / 面試現場 demo

一句話:**企業把自己的資料放進一個資料夾,不改任何一行程式碼,就得到一個掛在 LINE 官方帳號上的 AI 客服。**

> **改版紀錄(2026-09-21)**:本文第一版採用 Cloudflare Worker + Dify Cloud。
> 同日改為 **FastAPI + 自建 Agent + 資料庫**。原因:Worker + Dify 設定檔證明的是
> 「會設定工具」,FastAPI + 自己設計的 schema 證明的是「會做系統」,後者能講的故事是
> 前者的超集,而且真的用得上課程學的技術。原版仍在 git 歷史中。

## 一、目標與範圍

### 三個核心需求對應到哪裡

| 需求 | 設計中的位置 |
|---|---|
| AI 智慧客服,**不侷限餐飲** | `industries/` 一個行業一個資料夾。行業是參數,不是寫死的 |
| **各個企業**能使用 | 五份 YAML + `companies` 資料表。換企業 = 複製資料夾、改 YAML、重新 seed |
| 串接 **LINE 客服** | `/webhook/{slug}`,系統唯一的對外入口 |

「各個企業能使用」的定義是**由導入者(作者)替每家企業設定**,不是企業自己註冊。
v1 沒有註冊頁與租戶後台;但資料表已照多租戶設計,之後要做成客戶自助的 SaaS 不必改表。

### 做(v1)

1. **FastAPI 服務** —— 收 LINE webhook、驗簽章、組 prompt、呼叫 LLM、回訊息。
2. **資料庫** —— PostgreSQL(正式)/ SQLite(開發測試),SQLAlchemy ORM + Alembic。
   四張表的詳細設計見 [2026-09-21-schema-draft.md](2026-09-21-schema-draft.md)。
3. **YAML 資料層** —— 行業無關的五份 YAML,經 validate 後 seed 進資料庫。
4. **三個示範行業** —— 餐飲、電商、診所。
5. **部署到公開 HTTPS** —— 否則 LINE 根本連不到。

**v1 的里程碑**:拿手機傳訊息給 LINE 官方帳號,客服會用餵進去的資料回答、記得上一句話;
換一個 `--industry` 重新 seed 就變成另一個行業。

### 不做(v1 明確排除)

| 項目 | 為什麼延後 | 現在先做什麼 |
|---|---|---|
| **多租戶管理介面** | 成本不在 schema,在金鑰輪替、隔離測試、租戶後台 | `companies` 表照建,v1 只放一列。之後開多租戶不用改表 |
| **真人接手介面** | 沒有客服後台,`HUMAN` 模式切進去就沒人切得回來 | `mode` / `mode_expires_at` 欄位照建,v1 不寫入 |
| **RAG(Qdrant)** | 五份 YAML 的內容塞得進 context,還不需要檢索 | `knowledge_documents` 表照建但不寫入。知識超過 context 時才是它上場的時機 |
| **Text2SQL** | 要先知道客服真正會被問什麼查詢 | — |
| **對話分析報表** | 要先有真的對話才有東西分析 | `chat_histories` 已存 `latency_ms` / `token_count`,資料先累積 |
| 圖片 / 貼圖 / 語音訊息 | v1 只處理文字 | 回一句「我目前只看得懂文字訊息」 |
| 群組對話 | 只處理 1 對 1 | — |

### 聲明

這是**面試用的專題**,不是營運系統。取捨因此是:

- **成本不重要、防濫用不重要** —— 但 **demo 不能開天窗**。網路或 LLM 出狀況時,
  它必須講一句得體的話,不能已讀不回。
- **要有故事可講** —— 每個決策都要能用一句話解釋「不這樣做會怎樣」。
  這份文件本身就是面試素材。

## 二、決策紀錄

| # | 決策 | 理由 / 不這樣做會怎樣 |
|---|---|---|
| 1 | **FastAPI + 自建 Agent,不用 Dify** | `chat_histories` 存「LLM 短期記憶」就代表對話狀態自己管,而 Dify 本來也幫你管 —— 兩套並存只會有兩份不同步的紀錄 |
| 2 | Webhook 收到就回 200,工作丟背景 | LINE 沒收到 2xx 會重送。同步等 LLM(3–15 秒)必定超時,客人收到兩次一樣的答案 |
| 3 | 背景任務用 `BackgroundTasks`,不引入 Celery | 專題規模不需要訊息佇列。**代價要寫清楚:程序重啟會掉未完成的任務** —— 可接受,最壞情況是客人沒收到一則回覆,而 LINE 的重送機制會補上 |
| 4 | 回覆以 `replyToken` 為主,超時改 push | reply token **只有一分鐘、只能用一次**,官方明講「不要依賴這個時限」。但 push 會吃推播額度,reply 不會 |
| 5 | 去重靠 `line_message_id` 的 unique 索引 | 自己寫「先查再寫」有 race condition。讓資料庫擋,撞鍵就代表處理過了 |
| 6 | 簽章用 **raw bytes** 計算 | 必須 `await request.body()` 拿原始位元組。**在 FastAPI 裡這是個陷阱**:一旦宣告 Pydantic body model,框架已經 parse 過,再序列化回去位元組就變了 |
| 7 | 每家公司一個 webhook 路徑 `/webhook/{slug}` | 另外兩種做法都不行:逐一試 secret 是 O(n) 次 HMAC;只靠 body 的 `destination` 等於**在驗證前就信任了 body** |
| 8 | LINE 憑證加密存(Fernet) | 明文等於把別人官方帳號的控制權放在 `SELECT *` 裡。這是多租戶 SaaS 的基本考題 |
| 9 | YAML 是真相來源,seed 進資料庫 | 保住 validate 的 BLOCK 清單(這個專題最值錢、別人抄不走的部分),執行期又是乾淨的資料庫查詢 |
| 10 | LLM 用 OpenRouter | 既有金鑰與踩坑經驗都現成(見第六節第 4 坑) |
| 11 | 顯示名稱中文、路徑英文 | 多數 PaaS 的服務名只允許小寫英數與連字號;中文 GitHub 網址會變成百分號編碼,而這個連結要貼給面試官 |

## 三、整體架構

```
   industries/<行業>/*.yaml          ← 企業帶入的資料,唯一真相來源
            │
            │  python -m app.cli seed --industry <行業>
            │     ├─ validate  → ERROR 擋下 / BLOCK 列為導入議程
            │     └─ Jinja2    → system_prompt
            ▼
      ┌──────────────┐
      │  PostgreSQL  │  companies / users / chat_histories / knowledge_documents
      └──────┬───────┘
             │
  LINE ──────┼──────► FastAPI ──────► OpenRouter (LLM)
   ▲         │      /webhook/{slug}
   └─ reply ─┴─ push
```

**邊界**:`app/line/` 完全不知道客服在講什麼行業;`app/agent/` 完全不知道前台是 LINE。
之後要加 Web 聊天視窗,只是多一個 router。

## 五、請求流程

```
LINE ──POST /webhook/{slug}──> FastAPI
   │
   │ 1. await request.body() 取 raw bytes(不經 Pydantic)
   │ 2. 依 slug 查 company → 解密 channel_secret
   │ 3. 驗 X-Line-Signature = base64(HMAC-SHA256(secret, raw bytes))
   │       不符 → 401
   │ 4. 這時才 parse JSON。events 為空 → 200 結束
   │       (Console 按 Verify 時就是空 events + 全 0 的 replyToken)
   │ 5. 交叉比對 body 的 destination 與 company.line_destination,不符 → 401
   │ 6. ★ 回 200,其餘工作交給 BackgroundTasks
   │
   └─ 背景 ─┐
            │ 7. ★ 開一個「新的」DB session(見第六節第 1 坑)
            │ 8. upsert user(company_id, line_user_id)
            │ 9. 寫入 user 訊息 → IntegrityError 代表重送,直接結束
            │10. 取最近 N 則 → 組 prompt(人設 + 歷史 + 這一句)
            │11. 呼叫 OpenRouter(有 timeout)
            │12. 寫入 assistant 訊息(含 latency_ms / token_count)
            └13. reply(替代:push)──> LINE ──> 客人
```

## 六、五個必須擋掉的坑

### 1. 背景任務用了已經關閉的 DB session

**最容易中、而且症狀最誤導人的一個。** FastAPI 的 `Depends(get_db)` 產生的 session,
在 response 送出時就被關掉了。`BackgroundTasks` 在那之後才跑,拿到的是死的 session ——
錯誤會是 `DetachedInstanceError` 之類完全指不到真正原因的東西。

**背景任務必須自己開 session**,而且只傳「值」進去(company_id、文字),不要傳 ORM 物件。

### 2. 簽章用序列化過的 body 計算

必須用收到的原始位元組。在 FastAPI 裡的具體形式是:**router 不能宣告 Pydantic body model**,
要用 `Request` 拿 `await request.body()`,驗完簽章後才自己 `json.loads`。

寫測試時兩邊用同一個序列化器所以一定會過,LINE 真的傳過來(欄位順序、空白、Unicode 跳脫
都可能不同)就會全錯。**測試必須包含一組「已知 body 字串 + 已知 secret + 已知簽章」的固定樣本。**

> 呼應既有教訓:語音 demo 的所有測試都用 stub 跑,真的 SpeechRecognition 一次都沒驗過,
> 結果桌機全過、實機全壞。

### 3. 免費方案休眠 = 面試第一則訊息沒反應

Render / Railway 免費方案閒置會休眠,冷啟動數十秒。LINE webhook 等不了,
**第一則訊息沒反應、第二則才會動** —— 而這正好是面試官剛拿起手機的那一刻。

解法三選一:定時 ping 不讓它睡、求職期間付費、或 Cloudflare Tunnel 從筆電打洞。
**建議付費**,這是整個專題最不值得省的地方。

### 4. OpenRouter 會用 HTTP 200 包著錯誤回來

實測過:provider 暫時滿載時,回的是 200 但 body 裡是 error 物件。
**只看 `response.ok` 會誤判成功**,然後拿到空字串當答案送給客人。
判斷標準必須是「有沒有真的拿到 message 內容」。

同一支既有專案還踩過:推理模型會把內部思考當答案輸出(要關 reasoning、`max_tokens` 給足);
`openrouter/free` 自動路由每次隨機挑模型、品質跳動,應指定型號並保留退回機制。

### 5. 答案超過 LINE 的訊息長度上限

LINE 單則文字訊息上限 5000 字元,超過**整則失敗,客人什麼都收不到**,
錯誤只留在伺服器 log 裡。送出前截斷。

不分則 —— 分則會讓客人收到一串沒頭沒尾的訊息,而客服答案本來就不該那麼長:
會超過上限本身就是資料寫壞了,應該在 validate 階段就發現(見第七節規則 4)。

## 七、資料層:五份 YAML

每個行業一個資料夾,結構完全相同。**新增行業 = 複製資料夾、改 YAML、重新 seed。**

| 檔案 | 內容 | 必填 |
|---|---|---|
| `company.yaml` | 公司名、業別、營業時間、聯絡方式、語氣、**禁語清單** | `name` `industry` `hours` `contact` `tone` `forbidden_phrases` |
| `faq.yaml` | 常見問答,量最大的一份 | 每筆 `q` `a`,`a` 不可為空 |
| `policies.yaml` | 退換貨、保固、預約、付款、隱私 | 每條 `title` `content` |
| `escalation.yaml` | 分級與轉真人規則 | 每條 `level`(L1/L2/L3)`trigger` `action` `script` |
| `glossary.yaml` | 行業術語表,避免模型講錯專有名詞 | 每筆 `term` `meaning` |

`escalation.yaml` 是最值錢的一份。客訴分級、什麼情況必須轉真人、什麼話絕對不能說 ——
規則跨行業通用,但**只有真的在第一線處理過客訴的人寫得出來**。這是整個專題裡別人抄不走
的部分,結構沿用 `bistro_concierge/knowledge/complaints.yaml` 的 L1/L2/L3 階梯。

### validate 規則

兩個等級的意思不同:**ERROR = 資料壞了,擋 seed**;**BLOCK = 資料沒壞,但不該就這樣
交給客戶上線**,不擋 seed,但列在報告最上方,要在導入會議上確認過才算解除。

| # | 檢查 | 等級 |
|---|---|---|
| 1 | 五份 YAML 都存在且可 parse | ERROR |
| 2 | 必填欄位齊全 | ERROR |
| 3 | **FAQ 的答案本身不可命中自己的 `forbidden_phrases`** | ERROR |
| 4 | 任一答案長度超過 LINE 上限 | ERROR |
| 5 | `escalation` 必須涵蓋四類高風險:法律、醫療/人身安全、金錢爭議、個資 | BLOCK |
| 6 | 殘留 placeholder(`請填入` / `TODO` / `XXX`) | BLOCK |
| 7 | `glossary` 的術語不可與禁語清單衝突 | ERROR |
| 8 | 營業時間格式可解析 | ERROR |

> **BLOCK 不是 bug,是導入會議的議程。** 面試時最值得講的一句話:交付的不是機器人,
> 是一份檢查清單 —— validate 跳出來的每一條,都是要跟客戶確認的問題。
> (概念沿用 `bistro_concierge/src/validate.py` 的 17 項 BLOCK。)

### 三個示範行業

| 行業 | 它壓測到什麼 |
|---|---|
| **餐飲** | 基準線。作者的專業領域,資料寫得最真 |
| **電商** | 退換貨、物流、付款這類**規則密集**的問答 |
| **診所** | **escalation 與禁語的價值**:不能給醫療建議、不能判斷病情、必須轉真人。沒有這個行業,`escalation.yaml` 和 validate 第 5 條看起來只是多餘的規則 |

## 八、錯誤處理與降級

| 情況 | 行為 |
|---|---|
| slug 查無此公司 / 公司停用 | 404,不處理 |
| 簽章不符、destination 不符 | 401,不回訊息 |
| `events` 為空(Console 的 Verify) | 200,結束 |
| 非文字訊息 | 回「我目前只看得懂文字訊息」 |
| `line_message_id` 撞鍵(重送) | 略過,不回訊息 |
| LLM 逾時 / 錯誤 / 空回應 | 回 `company.fallback_message` |
| 答案超過長度上限 | 截斷並附「(訊息過長已截斷)」 |
| reply 失敗(token 過期或已用) | 改用 push 送同一則 |
| push 也失敗 | 寫 log,放棄。重試只會讓客人收到延遲很久的孤立訊息 |

**原則:任何情況下客人都要收到一句話。沉默是唯一不被接受的失敗模式。**
網路出狀況時它講了一句得體的話,比它答對十題更能說明設計者想過真實情境。

## 九、測試策略

`pytest` + `httpx.AsyncClient` + SQLite in-memory。只 mock 對外的 HTTP(OpenRouter、LINE),
資料庫跑真的。

| 測什麼 | 為什麼非測不可 |
|---|---|
| 簽章驗證(**固定樣本**:已知 body 字串 + secret + 簽章) | 防第六節第 2 坑的唯一手段 |
| 簽章不符 → 401 且完全不呼叫 LLM | — |
| 空 events → 200 且不呼叫 LLM | Console 的 Verify 會送這個 |
| 同一 `line_message_id` 送兩次 → LLM 只被呼叫一次 | 決策 5 |
| 背景任務能在 response 之後正常存取資料庫 | 防第六節第 1 坑 |
| 短期記憶:第二則請求的 prompt 裡含第一則的內容 | — |
| LLM 逾時 → 走 fallback,而且**有送出訊息** | 沉默是唯一不被接受的失敗 |
| OpenRouter 回 200 但 body 是 error → 視為失敗 | 第六節第 4 坑 |
| reply 失敗 → 自動改走 push | — |
| 超長答案被截斷 | — |
| 三個行業都 seed 成功、validate 零 ERROR | — |
| 故意抽掉必填欄位 / 讓 FAQ 命中禁語 / 拿掉醫療 escalation → 對應規則抓得到 | validate 自己也要被測 |
| 租戶隔離:A 公司的 userId 查不到 B 公司的對話 | 即使 v1 只有一家,這條要先立起來 |

**端對端(手動,不可省略)**:LINE Console 按 Verify 通過 + 真的用手機傳四則訊息
(一般問答、接續前一句、觸發 escalation、傳一張圖)。

> 既有教訓:所有語音測試都用 stub 跑,真實裝置一次都沒驗過,結果桌機全過、實機全壞。

## 十、驗收標準

1. `python -m app.cli seed --industry restaurant|ecommerce|clinic` 三個都成功,validate 零 ERROR
2. 服務部署在公開 HTTPS,LINE Console 的 Webhook「Verify」顯示成功
3. 手機傳訊息,收到符合該行業資料的回答。典型 10 秒內;超過 60 秒仍要收得到(走 push)
4. 連續兩則訊息,第二則看得出記得第一則(短期記憶)
5. 診所版問「我這個症狀是不是癌症」→ 觸發 escalation,拒答並提供轉真人指引
6. 故意把 LLM 金鑰改壞 → 客人收到 fallback 文案,不是沉默
7. 資料庫裡看得到 `latency_ms` 與 `token_count`
8. 冷啟動問題已處理(付費 / 定時 ping / Tunnel 三選一,並實測第一則訊息有反應)
9. 全部自動測試通過
